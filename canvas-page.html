🎯 Overview

A linked list has to walk from the front to find anything, so looking up one value out of a thousand means up to a thousand steps. A hash table turns the key itself into an index — it computes where the value should be and goes straight there, in roughly constant time no matter how much data is in the table.

Two keys can land on the same index, and that is the whole problem this activity solves. Separate chaining gives each bucket its own linked list, so a collision just means a slightly longer chain to walk. You are writing the table behind a professor’s grade book: insert a student, look up a grade, drop a student, and grow the table before the chains get long enough to matter.

One file of implementation, 10 TODOs, plus four in main.cpp that drive the demo. Worth 30 points, and you can check your own score at any time.

📖 Learning Objectives

By completing this activity, you will be able to:

  • Explain how a hash function maps a string key to a bucket index, and why the modulo step is what keeps it in range
  • Implement the multiply-and-add hash and explain why resizing invalidates every index it produced
  • Resolve collisions with separate chaining — an array of linked lists, one chain per bucket
  • Write insert so that an existing key is updated rather than duplicated
  • Reuse the trailing-pointer pattern from CT 09 to unlink a node from the middle of a chain
  • Define load factor and explain why the table grows before it is full, not after
  • Explain why chaining is O(1) on average and O(n) in the worst case, and what makes the difference

Part 1: The Constructor and Destructor

File: src/ChainingHashTable.cpp — TODO 1 and TODO 2

The table is an array of chain heads. TODO 1 allocates that array with capacity_ slots and zero-initializes it, so every bucket starts as nullptr — an empty chain.

buckets_ = new ChainNode*[capacity_]();   // the () zero-initializes

Without the () the pointers hold garbage, and the first thing that walks a chain will follow one of them and crash. The destructor is the mirror image and has to free in the right order: delete every node in every chain first, then delete[] buckets_. Free the array first and you have thrown away the only pointers to the nodes.

Checkpoint: nothing scores yet, but the program should build and run without crashing. Everything after this depends on both of these being right.

Part 2: hash() — Turning a Key Into an Index

File: src/ChainingHashTable.cpp — TODO 3, worth 4 points

Two steps. Fold every character into a running total, then bring that total into range:

size_t hash_value = 0;
for (char c : key) {
    hash_value = hash_value * 31 + c;   // multiply-and-add
}
return hash_value % capacity_;          // land it in [0, capacity_)

The multiply by 31 is what makes position matter — without it "abc" and "cba" would hash identically. The modulo is what guarantees the result is a usable index.

Note what this means for resize() later: the index depends on capacity_, so changing the capacity changes where every existing key belongs. That is why resizing has to rehash rather than copy.

Checkpoint: HashFunction.ConsistentResults and HashFunction.WithinRange pass — 4 points. They check that the same key always lands in the same bucket, that every index is in range, and that your keys do not all pile into one bucket.

Part 3: insert() — Add, or Update in Place

File: src/ChainingHashTable.cpp — TODO 4, worth 8 points

This is the largest single block of points on the page, because it is two jobs in one. Hash the key, then walk that bucket’s chain:

  • If a node already holds this key, overwrite its value and stop. Do not add a second node — a grade book with Bob in it twice cannot answer what Bob’s grade is.
  • Otherwise build a new node and put it on the front of the chain, then increment size_.

Prepending is O(1); appending would have to walk to the end first, and nothing about a chain cares which order it is in.

Checkpoint: all three ChainingInsert tests pass — 8 points. HandlesCollisions is the one that proves the chain works: it inserts two keys that hash to the same bucket and expects both to survive.

Part 4: search() — Find a Value by Key

File: src/ChainingHashTable.cpp — TODO 5, worth 6 points

The same two-step shape as insert: hash to a bucket, walk its chain comparing keys. Return &current->value on a match so the caller can read it, or nullptr if you reach the end of the chain.

Returning the address rather than a copy is what lets main.cpp print a grade without the table handing out its internals — and it is why the method is const: it may read the table, never change it.

Returning nullptr every time will not score. The tests check that a key you just inserted is found, not only that a missing key is not.

Checkpoint: all three ChainingSearch tests pass — 6 points.

Part 5: remove() — Unlink a Node From a Chain

File: src/ChainingHashTable.cpp — TODO 6, worth 6 points

This is CT 09’s trailing-pointer pattern again, applied one bucket at a time. A node does not know who points at it, so you carry a previous pointer one step behind current:

ChainNode* previous = nullptr;
ChainNode* current  = buckets_[index];
while (current) {
    if (current->key == key) {
        // previous == nullptr means this is the head of the chain
        ...
    }
    previous = current;
    current  = current->next;
}

Two cases to get right. If previous is still nullptr the match is the head, so the bucket itself has to point past it. Otherwise previous->next skips the node. Either way: delete the node, decrement size_, and return true. A key that is not there returns false and changes nothing.

Checkpoint: all three ChainingRemove tests pass — 6 points, including removing from the middle of a collision chain.

Part 6: load_factor() and resize() — Growing Before It Hurts

File: src/ChainingHashTable.cpp — TODO 7 and TODO 8, worth 6 points

load_factor() is one line — entries divided by buckets — but cast before you divide or integer division gives you 0:

return static_cast<double>(size_) / capacity_;

resize() is where the hash function’s dependence on capacity_ comes due. Every key’s index is computed with the old capacity, so a bigger array means they all belong somewhere else. You cannot copy the buckets across — you have to rehash each entry into the new array.

The table grows when the load factor crosses the threshold, not when it is full. Chains are still short at that point, which is exactly the moment the table is cheap to rebuild.

Checkpoint: both ChainingResize tests pass — 6 points. AllEntriesSurvive is the one that catches a rehash that dropped something.

Part 7: print() and the Grade Book

Files: src/ChainingHashTable.cpp (TODO 9) and src/main.cpp (4 TODOs) — not directly scored

print() walks every bucket from 0 to capacity_ - 1 and shows its chain. No test scores it, but it is the fastest way to see a collision: insert the five students and look at which buckets ended up with two names.

main.cpp drives the demo in four steps — insert five grades, print the table and its load factor, search for a student who is there and one who is not, then update Bob and remove Diana. Working through it is how you confirm the table behaves the way the tests say it does.

🔧 Common Problems

The build fails, or CMake does not configure

Check the bottom-left corner of VS Code reads Dev Container. If it does not, press Ctrl+Shift+P and run Dev Containers: Reopen in Container — with Docker Desktop running. Still stuck? Delete the build/ folder and run cmake -B build again.

Every key lands in bucket 0

hash() is still returning the stub’s 0, or you did the modulo before the loop instead of after it. The multiply-and-add runs over the whole key first; % capacity_ happens once, on the way out.

Inserting the same key twice gives two entries

The update case is missing. Before you prepend a new node, walk the chain and look for the key — if it is there, overwrite value and return without touching size_.

Crash the first time anything walks a chain

The bucket array was allocated without zero-initializing it, so the pointers are garbage rather than nullptr. The () at the end of new ChainNode*[capacity_]() is what makes every bucket an empty chain.

RemoveFromCollisionChain fails

Almost always the head case. When the node you are deleting is first in its chain, previous is still nullptr — the fix is to point buckets_[index] at current->next, not previous->next.

load_factor() always returns 0

size_ / capacity_ is integer division, so anything below 1.0 truncates to zero. Cast the numerator first.

AllEntriesSurvive fails after a resize

The old entries were copied into the new array at their old indices. They have to be re-hashed — the index depends on capacity_, and capacity_ just changed.

Tests fail to build

The test file is not yours to edit — if it will not compile, a signature in ChainingHashTable.cpp no longer matches the header. Compare the method names, parameter types and const markers against include/ChainingHashTable.h.
